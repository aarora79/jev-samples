pr-triage: one pull request, one call, one tier

Jev answers eleven questions in a single call. Python does every piece of arithmetic.

1

Read one pull request

Title, description, the file list, and as much of the diff as the budget holds. A patch too large to send whole arrives as whole files first, then paths and line counts.

2

Ask eleven questions, in one call

Every question sees the same pull request. None sees another's answer, so the eleven cost the tokens of eleven and the wall clock of about one.

Nine scored, and weighted

How far the change reaches, whether it touches auth or secrets, how many judgment calls it holds, whether it breaks a caller, whether it ships tests, and four more.

Two labels, never scored

What kind of change: docs, tests, dependency, config, bugfix, feature or refactor.
What to check first: correctness, security, compatibility, tests, deployment or readability.
Both print beside the tier.

3

Average the nine into a review load

Each answer counts for the weight questions.yml gives it, and three of them count inverted, so a mechanical diff, a tested change and a thorough description each pull the load down. The weights sum to 1, so the load runs 0.00 to 1.00.

4

Read the load as a tier

high
0.62 and up
medium
0.42 to 0.62
low
0.22 to 0.42
trivial
under 0.22

A load within 0.02 of a cut prints (on a cut), because repeat calls move it by that much.

5

Let the file and line counts raise it

over 30 files or 1,500 lines → high
over 12 files or 500 lines → medium
over 4 files or 150 lines → low

Jev reads a truncated diff, so a 54-file change can read as one repeated edit. Size is arithmetic, Python owns it, and it only ever raises a tier.

6

Print one line per pull request

The tier, the advice that goes with it, and the questions that drove the load. Every run also writes a JSON report and a markdown one into data/.
