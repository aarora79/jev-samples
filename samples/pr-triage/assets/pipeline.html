pr-triage: one pull request, one call, one route

Jev answers eleven questions in one call. Code does every piece of arithmetic, and the output is a route rather than a merge.

1

Read one pull request

Title, description, the file list, and as much of the diff as the budget holds. A patch too large to send whole arrives as whole files first, then paths and line counts.

2

Stop early on anything that is not reviewable

One call to the checks API per pull request, before any Jev call. Three states are terminal: no questions asked, no route computed, nothing spent. On eighteen apache/airflow pull requests this skipped ten of them.

StateMeansWaiting on
ci-failinga check concluded failure, timed out, or wants actionthe checks, or the branch
ci-pendinga check is still runningnobody, come back later
draftthe author marked it draftthe author, who is not asking

A name that fails on several unrelated pull requests is the check being broken rather than each change breaking it: a boto3 bump cannot break Postgres serialization. Five of eight failures were shared that way, and the output says so, because the state is a fact and never a verdict on the author.

3

Ask eleven questions, in one call

Every question sees the same pull request. None sees another's answer, so the eleven cost the tokens of eleven and the wall clock of about one.

Nine scored, and weighted

blast radius how far it reaches · security surface auth, secrets, tokens, input validation · breaking change a caller stops working · infra surface deploy, images, CI · design decisions judgment calls to agree with · mechanical one edit repeated · scope creep the diff exceeds the description · has tests the change is covered · description quality what, why, and how they checked

Two labels, never scored

What kind of change: docs, tests, dependency, config, bugfix, feature or refactor.
What to check first: correctness, security, compatibility, tests, deployment or readability.
Both print beside the route.

4

Read the answers on two axes, not one

Effort and consequence are different questions, and they take different arithmetic.

Effort: the weighted mean of nine

All nine, at the weights in questions.yml: blast radius 0.15, security surface 0.15, design decisions 0.14, mechanical 0.12, breaking change 0.11, scope creep 0.09, infra surface 0.08, has tests 0.08, description quality 0.08.

Averaging is right here, because a diff that is long in one way and short in three really is a medium read. Mechanical, has tests and description quality count inverted, so a repeated edit, a covered change and a thorough description each pull it down.

Consequence: the max of four

Four of the same nine, read differently: security surface (auth, secrets, tokens), breaking change (an existing caller stops working), blast radius (reaches shared code paths), infra surface (deploy, images, CI).

The max, never the mean, because a change that is safe in three ways and dangerous in one is a dangerous change. A score reads the probability on its top level only: blast radius level 1 is "one module", which is ordinary work.

5

Turn the pair into a route: what would be enough to merge

Consequence sets the floor. Effort can raise it and never lower it. Nothing here says "merge", because a model reported at 67.8% accuracy can decide how much evidence to demand and cannot be the last gate before main.

6

Let the file and line counts raise the effort tier

over 30 files or 1,500 lines → high
over 12 files or 500 lines → medium
over 4 files or 150 lines → low

Jev reads a truncated diff, so a 54-file change can read as one repeated edit. Size is arithmetic, Python and Go own it, and it only ever raises.

7

Print the route, the reason, and the one thing that would change it

Grouped by route, with what set the consequence, the questions carrying the effort, and the single signal that would drop it a route: "a test that exercises the unconnected-identity path". A tier tells an author nothing to do. That line does.
